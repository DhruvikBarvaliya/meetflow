MeetFlow Audit vs. MEETFLOW_ONLY_MASTER_PROMPT.md develop @ 0dbe28c

What the spec asked for, and what is actually there

Eight auditors, working from the original 2,081-line specification rather than from anyone's memory of it. Fifty-three findings.

Verdict

Not complete against the spec's own release checklist — but the incompleteness sits at the edges, not the core. The engineering that is hard to fake is done properly: booking concurrency is enforced by real PostgreSQL exclusion constraints and proven by a ten-way race test, DST is handled in both directions, tenant reads answer 404 rather than 403, and 130 mounted routes match 130 OpenAPI operations and 130 Postman requests exactly.

What fails is the last mile. Three of the four workspace roles cannot be reached in a fresh deployment. One advertised subsystem has a model, a migration, a processor, a queue and a dedicated worker — and no possible way to execute. The tenant's own audit trail is write-only. And the repository's own quality gates were red.

Tier 1 — breaks the spec's definition of success

These are the ones that would show up in a demo or a client audit.

01
Blocking Effort: medium

No member can ever be added to a workspace

Membership.create has exactly one call site in the entire codebase — workspace creation. There is no invite endpoint, no role-change endpoint, no removal endpoint. Manager, Receptionist and Staff are unreachable outside the seeder, so the RBAC engine that the tests prove correct has no way to be exercised in a real deployment. The permissions members:invite, members:update, members:remove and roles:manage are granted to roles and enforced by zero routes.

server/src/modules/businesses/business.service.ts:182 — sole call site · business.routes.ts exposes only GET /members · verified directly

02
Blocking Effort: large

The Customer role does not exist as an identity

User.platformRole is only ADMIN | USER. The customer portal lives under /app, and ProtectedRoute sends any signed-in user with zero memberships to /create-workspace. The net effect is that the customer dashboard the spec devotes a section to is reachable only by an owner or manager whose email happens to match a customer record. The README's claim that seeded customers have portal accounts is misleading as written.

client/src/components/layout/ProtectedRoute.tsx:64-66 · client/src/pages/customer/useMyCustomer.ts:36

03
Blocking Effort: small

The workspace audit trail is write-only

Eighteen services write audit rows and no tenant can read them. The spec names GET /api/v1/audit-logs; only the platform-admin version exists. audit:read is granted to Business Owner and Manager and enforced by no route at all. The reader already exists in the admin service and could be reused almost verbatim.

no /audit-logs on the management router — verified directly · reader exists at admin.service.ts:1298-1345

04
Blocking Effort: small to disclose

The webhook subsystem cannot run, and is listed as shipped

fanOutEvent has zero callers repo-wide. There is no webhooks module, no router, and no way to create an endpoint except by hand in psql — which the spec explicitly forbids. A dedicated worker consumes a queue nothing writes to. Meanwhile Changelog.md:57 lists “webhook delivery with HMAC signing” under Added.

This is the only place in the repository where a document claims something the code cannot do, and it is the one finding that undercuts an otherwise unusually honest posture.

Tier 2 — security and correctness

Nine defects. Two are genuine security holes; the rest are correctness bugs with user-visible consequences.

08
Security Effort: small

HTML injection into outgoing email

At enqueue, template placeholders are substituted unescaped. At delivery, textToHtml re-runs the renderer with escaping on the already-substituted string — so it escapes only placeholders that no longer exist — then interpolates each line raw into <p>${line}</p>. A public booking with a first name of <img src=x onerror=…> lands in the recipient's inbox as live markup.

The escaping is real; it simply runs one render too late. docs/NotificationArchitecture.md claims the protection that the code does not provide.

templates.ts:359-372 · notification.service.ts:100-110 · traced end-to-end and confirmed

09
Security Effort: small

EMAIL_PROVIDER=console is not blocked in production

The env layer has production guardrails for seeding, rate limiting, log formatting, placeholder JWT secrets and insecure origins — and none for the email provider, which defaults to console. A production deploy on defaults marks every confirmation and every reminder SENT while sending nothing at all.

server/src/config/env.ts:116 — default console, no production guard — verified directly

10
Security Effort: small

Auth rate limiting does not stop password spraying

The bucket key is IP|email, so one host can try one password against unlimited accounts — each email is a fresh bucket, and the per-account lockout (one failure each) never trips. The comment directly above the resolver claims the opposite. The same resolver on /auth/register permits unbounded mass account creation from a single IP, and the limiter fails open on internal error.

server/src/middleware/rateLimit.ts:137-150 — read and confirmed

11
SecurityEffort: small

Socket sessions survive “log out everywhere”

authenticateSocket re-reads the user and membership but never the refresh-token family, so a revoked session keeps receiving live workspace events until its access token expires. The HTTP path closes this hole; the socket path does not.

grep RefreshToken server/src/sockets/index.ts → no match

12
CorrectnessEffort: small

The booking horizon is not enforced at confirmation

maxHorizonDays clamps the availability search range and is never re-checked at commit. A caller supplying an explicit staff id can book years past the horizon. No test covers it.

availability.service.ts — horizon absent from verifySlot and createBooking

13
CorrectnessEffort: small–medium

Reschedule and reject leave stale reminders queued

Only the cancel path touches pending notifications. A rescheduled customer keeps reminders at the old time, carrying a payload frozen at booking — reminded at the wrong hour about the wrong appointment. A rejected customer is still reminded about a booking that was refused.

lifecycle.service.ts:549 is the only Notification.update

14
CorrectnessEffort: medium

Shared resources can be oversubscribed by a reschedule

Reschedule moves resource rows with a bare UPDATE, skipping the SELECT … FOR UPDATE capacity check. Exclusive resources stay protected by the exclusion constraint; resources with capacity > 1 do not.

lifecycle.service.ts:329-332 — auditor's line cite, not independently re-verified

15
CorrectnessEffort: small–medium

Notifications can strand in PROCESSING forever

The recovery sweep filters on PENDING, so a hard kill between claim and catch strands the row permanently — and the queue's stalled-job retry finds nothing to claim and reports success. The architecture doc's claim that a dying worker cannot strand a message holds only for handled exceptions.

grep "'PROCESSING'" server/src — single writer, sweep excludes it

16
CorrectnessEffort: small

Account lockout does not escalate, and is untested

Eight failures buy a fifteen-minute lock — then the counter resets to zero, so every fifteen minutes buys another eight attempts. The comment calls it “progressive lockout”; nothing escalates. No test at any level drives an account into lockout.

auth.service.ts:29-30, 252-256 · no lockout test anywhere

Things the auditors flagged that are actually fine

Each auditor saw one slice. These were overruled on review.

Twelve false alarms
  • Cross-tenant 404 instead of 403. Correct, deliberate, commented and tested at two levels. This is right.
  • Consolidated ADR file. The spec names no file-per-record convention. A numbered, status-bearing append-only log satisfies it. Only the two missing decisions count.
  • Missing server/src/services/. The spec permits a clear architectural reason; per-module service files preserve the separation the rule protects.
  • Idempotency in Postgres rather than Redis. Postgres is the stronger choice. Only the doc advertising a Redis fast path is wrong.
  • Client image runs as root. The nginx master is root and workers drop privileges — stock upstream behaviour, with no-new-privileges set.
  • Off-grid booking accepted. Deliberate, commented, and covered by a test asserting the behaviour.
  • Unjoined socket rooms. The docs explicitly say they are reserved and nobody auto-joins.
  • npm audit's two criticals. Both vitest; the production image does a fresh install omitting dev dependencies.
  • PlaceholderPage.tsx being “deceptive”. It is dead code, but its content is an honest “not available yet” and renders no fake metric.
  • Three absent entities. The spec's data model explicitly permits a simpler relational design.
  • Reschedule metric counting a column rather than history rows. Same number in practice, deliberately chosen.
  • “Test claims unverified.” One auditor had no local Postgres and said so honestly; another executed everything.

What is genuinely solid

Worth knowing what not to re-check.

  • Booking concurrency. Five layers in the spec's own order, two real GiST exclusion constraints, proven by a ten-simultaneous-request test that yields exactly one appointment and a six-way group race that never oversells. The migration comment even explains why an exclusion constraint cannot express “at most N” for shared resources.
  • Timezones and DST. Luxon throughout, fixed offsets rejected, staff and business zones intersected as instants, no manual offset arithmetic anywhere. Both DST directions tested.
  • Tenant read isolation. 404 not 403, permissions re-read per request and never carried in the JWT, DENY beating GRANT, every lookup scoped by tenant in the same query.
  • Transactional outbox. Rows written inside the caller's transaction via savepoint, enqueued after commit, drained by a real worker in a separate container with backoff and a recovery sweep.
  • Security baseline. The env layer refuses to boot on weak or placeholder secrets, seeding enabled, or non-HTTPS origins in production. Every body schema is strict, so privilege escalation via an extra field is a 422.
  • Contracts, today. 130 routes = 130 OpenAPI operations = 130 Postman requests, zero drift on paths, request schemas, status codes or header wiring.
  • Database. Nine migrations up and down clean, 42+ tables, 158 indexes; every index and constraint the spec names confirmed live in pg_constraint.
  • Honesty of the source tree. Zero TODO, FIXME, HACK or XXX across every tracked file. No debugger, no .only, no empty catch, no mock data, no committed secrets. Every figure on all four dashboards traces to an API field.
